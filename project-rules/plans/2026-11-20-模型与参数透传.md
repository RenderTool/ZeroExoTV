# C-10 模型与参数真正下发（网页 = MCP，2026-11-20）

> 状态：本轮直接修，目标 0.4.34。用户实测：模型映射面板已选 int8 四件套，但网页提交的 payload 与 MCP 提交的 payload 都不完整；LoRA 由插件模板硬编码。

## 1. 现象（实测，非推测）

1. 网页 `buildDirectorBatchPayload` 每段 params 只有 12 个键（prompt/negative_prompt/width/height/frames/steps/cfg/seed/frame_rate/guide_frames/live_tae_preview*），共享参数里的 `sampler / scheduler / shift_video / shift_audio / clear_vram_between_segments / cache_frames_codec / cache_name / lora_name / lora_strength / use_low_vram` **全部没下发**。
2. 插件模板 `reference_video.json` 的占位符包含上述全部键，缺省时用 `TEMPLATE_DEFAULTS` 顶：**LoRA 恒为 `minimax_h3_ref2v_turbo_8step_v1.0_768p_comfyui_bf16.safetensors`**（8 步蒸馏），与用户面板 steps=12 直接冲突。这就是「每次生成都不对劲」的机械原因之一。
3. MCP 工具 `request_director_run` 的 schema **没有 models**，`buildDirectorPluginPayload` 返回的 payload 也不带 models → 走 MCP 必然退回模板自选（48G bf16 文本编码器）。
4. MCP 执行器上传参考图用 `references[].storageKey` 原值，**不解析主体树** → 主体换图后仍传旧图（`cas:23d2e809` 旧 key）。

## 3. 口径

- **白名单只放模板占位符里真实存在的键**（`reference_video.json` 里的 `__zx:*`），避免把 `aspect/scaleFactor/total_frames` 之类 UI 内部键塞进模板造成越权覆盖。
- 模型四件套**不做任何自动挑选/降档**；没配置就报错，让用户去模型映射选。
- LoRA（2026-11-20 补定）：链路里原来连键都没有，等于永远只能吃模板默认 8 步 turbo，所以本轮**在参数面板补了显式入口**（`LoRA` 文件名输入 + `LoRA 强度`，留空 = 模板默认）。仍然**不按步数自动挑 LoRA**，填什么都不替用户决定。
- dryRun 是纯预检：不连云端、不传图，输出「本段会用的模型 / 参数 / 参考图标题 / guide」；门禁（延续法计划、质检）只在真提交时生效。

## 4. 验收

1. `payload.params` 出现 sampler/scheduler/shift_video/shift_audio/lora_name（有值时）。
2. MCP `request_director_run` 不传 models 时读广播文件，云端任务记录 `models` 非空。
3. 未配置模型且非 dryRun → 报错文案明确指路模型映射面板，不再静默。
4. MCP 参考图上传使用主体树当前图（旧 key 换新 key）。
5. 单测：白名单只挑存在的键；MCP 读文件优先级；主体解析 4 种 origin 形态。
