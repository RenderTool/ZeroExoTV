# C-28 砍掉本地 fs 服务：网页只认浏览器目录授权

日期：2026-11-22

## 用户口径（原话要点）

- 网页就是网页：文件夹授权一次，之后不该再要求启动任何后台进程，否则变成 CS 架构。
- MCP 与网页用同一个路径即可，网页写下去 MCP 自己读得到，不需要通知机制。
- 不启动 MCP、不启动 ComfyUI，网页也应该正常打开、正常编辑、正常存盘。
- 不需要额外的 fs 服务，读写磁盘本来就是 MCP 自身的能力。
- 没有多机共享需求；将来真要多机共享，会上正经 Node 服务端（网页退化为客户端），与这个 fs 服务无关，不留"备用"。

## 现状/根因

1. `src/platform/http-fs.ts` 把 8790 服务当"数据权威"：探测成功即 `everOnline = true` 且 `markDataRootOrigin('service')` 持久化到 localStorage，此后 `dataRootExpectsService()` 恒为 true。
2. `fs.ts::dataRootState()` 在该标记下，即便用户已授权目录，也要 IDB 句柄 `queryPermission` 为 `granted` 才算通过；Chromium 跨会话常见状态是 `prompt`，于是返回 `service-offline`，`app.tsx` 渲染全屏 `ServiceOfflineGate`。
   同样是 `prompt`，非服务分支只判 `unauthorized` 并弹 `RootGate`（点一下即可）——同一状态两种结果，是本次报障的直接原因。
3. `boot.ts::bootReady` 首步 `await probeHttpFs({retry:false})`（1.5s 超时），且 `main.tsx` 必须等它完成才渲染；`index.html` body 纯白无占位 → 等待期即白屏。
4. 出片输入链路不依赖本地文件路径：`comfyui-bridge-client.ts:283` 用 `FormData` 直接 POST 二进制到 8188，ComfyUI 自行落 input 目录。因此删除 fs 服务不影响生成。

## 改动清单

**网页数据层（收敛为单一路径：浏览器目录）**
- 删除 `src/platform/http-fs.ts` 整个模块（探测、baseUrl、origin 标记、switch/stat/migrate/locate root 等服务端专用能力）。
- `src/platform/fs.ts`：
  - `DataRootState` 收敛为 `'ok' | 'unauthorized'`，`dataRootState()` 只判授权句柄；
  - 去掉 `httpFsReady` 前置 await（不得阻塞用户手势与首屏）；
  - `pickRoot()` 成功后写 `markDataRootOrigin('browser')` 的逻辑一并删除（不再需要 origin 概念）；
  - `currentDataRootPath()` 改为"用户登记的绝对路径提示（可选）或 null"，不再依赖服务返回。
- `src/platform/boot.ts`：删除 `probeHttpFs` 与相关 catch；`bootstrapDataRoot()` 直接走 FSA。
- `src/platform/data-root-events.ts`：删除 `DATA_ROOT_SERVICE_OFFLINE_EVENT`，只保留 `DATA_ROOT_AUTH_NEEDED_EVENT`。
- `src/platform/ServiceOfflineGate.tsx`：整文件删除。
- `src/app.tsx`：删除 `serviceOffline` 状态、探测 effect 中的该分支、`:492` 的离线门渲染；只剩 `RootGate`。
- `src/features/canvas-assets/groups/MaterialGroup.tsx`：删除 `service-offline` 文案分支，只保留"未授权"提示。
- 一次性清理 localStorage 残留键：`zeroexo.dataRootOrigin`、`zeroexo.httpFsBase`、`zeroexo.dataRootPath`（在首次启动时静默清除，避免旧安装继续被误判）。

**授权体验（"一次就够"）**
- `RootGate` 恢复授权时用 `ensure(handle,'readwrite', ask=true)`：Chromium 会弹"允许此网站编辑文件"，引导用户选成永久（`showDirectoryPicker` 本身每次都会弹，是浏览器设计，无法绕过）。
- `prompt` 状态一律走"点一下继续"，文案明确，不再出现全屏拦截。
- `index.html` 加原生启动占位（深色底 + 「正在启动…」）；`main.tsx` 改为 `Promise.race([bootReady, 1s])` 后必渲染。
- 页面级 `unhandledrejection` 兜底：错误画在页面上，不只进控制台。

**开发/构建侧**
- `vite.config.ts`：删除 `zeroexo-fs-server` 插件整块（dev/preview 不再拉起 8790）。
- `tools/start-fs-server.mjs`：删除。
- 根 `package.json`：删除 `fs`、`fs:build` 脚本。

**MCP 侧（保留本体，去掉 fs 服务形态）**
- `mcp-server/src/file-server.ts`：删除 `--fs-server` 模式与 8790 HTTP 文件服务实现。
- `mcp-server/src/index.ts`：删除 `--fs-server` 分支与相关提示。
- `mcp-server/test/file-server.test.ts`：随实现删除或改写为"目录解析"用例。
- MCP 数据根解析规则（写进 README/启动提示）：优先 `ZEROEXO_DATA_ROOT`；否则在常见盘符扫描含 `zeroexo-root.json` 的目录；均失败则报错要求显式指定。网页侧不做路径推送（浏览器不提供绝对路径）。

**测试**
- `src/platform/data-root-state.test.ts` 重写：仅 `ok` / `unauthorized` 两态；补"localStorage 有旧 origin=service 残留时仍按授权目录正常打开"回归用例。

## 风险与处理

- 大文件写入（视频、CAS）全走 FSA：已有 disk-driver 长期在用，无新增风险；需确认视频回写走流式而非整块内存。
- 旧安装的 8790 数据根（如 `D:\ZeroExoFinTest`）就是磁盘普通文件，删除服务不丢数据；用户授权该目录即读到同一批文件，需在指引里说明"选回原来那个文件夹"。
- 绝对路径展示能力下降：界面上只能显示文件夹名；需要绝对路径的地方改为用户可选登记一次，仅用于展示/给 MCP 指路。

## 验收

- 关掉全部后台进程（无 8790、无 MCP、无 ComfyUI），刷新网页：正常进入主页、可建项目、可编辑、可存盘，无白屏、无全屏拦截。
- 首次授权后，第二次打开只需一次"点一下继续"即可（给出永久授权则完全无需交互）。
- 启动 8188 后可直接出片；不启动时点"运行"给出"未连接出片服务"提示，其余功能不受影响。
- MCP 指向同一目录时，网页写入的文件 MCP 立刻可读。
- `tsc --noEmit` 零错误；相关测试通过。

## 不做

- 不做多机共享、不做远程数据根、不保留 `--fs-server` 备用形态。
- 不在网页侧内置任何 HTTP 文件服务。
- 不擅自重启任何进程、不改插件行为。
