# 主体库抽屉化可行性调研

日期：2026-11-05
性质：只读调研 + 设计结论，未改任何源码、未构建、未跑测试。
数据口径：全部取值自当前源码；视口高度按 900px 估算（列数结论不受 ±100px 影响）。

---

## 0. 结论（先给）

**不建议把主体库放进 480–560px 抽屉。**

三条硬数据：

1. 状态卡有 260px 最小宽度（`subject-card-metrics.ts` L12-15，gap 16）。抽屉 480/520/560 去掉内边距后内容宽 448/488/528 → **只能排 1 列**，一屏可见 2 张状态卡；整页 1440 是 4 列×3 行 = 12 张，1920 是 6×3 = 18 张。
2. 现有「留白」的主因不是"占整页"，而是列表页与状态编辑页的 `maxWidth: 1200`（`subject-library-pages.tsx` L551-558）：1920 屏有 708px 横向空边（38%），1440 屏 228px（16.5%）。抽屉不会修复这一点，它只是把空白换成"抽屉外面的画布"。
3. 抽屉会动摇三个稳定机制：四槽位固定页签模型（`canvas-tab-bar.tsx` L1-14）、发送直达上下文（`subject-send.ts`）、@ 素材面板的 `position: fixed` 定位（300px，`subject-media-source-panel.tsx` L275-279）。

**建议 C**：维持整页，落地上次的「单页三栏工作台」并取消列表页/编辑页的 1200 封顶，让宽度吃满。**若"不想让主体库独占屏幕、要边看画布/分镜"是硬需求，选 D**：可调宽停靠面板（≥640，默认 720），而不是固定 480–560 抽屉。A/B 不建议（理由见第 6 节）。

### 2.5 留白归因

| 现象 | 是 1200 封顶造成？ | 抽屉能修复？ |
|------|------------------|-------------|
| 1920 列表页左右大片空 | 是（708px） | 否（空白转移为画布背景，信息量不变） |
| 1920 编辑页左右大片空 | 是（708px） | 否（且表单可用宽从 1152 降到 448–528） |
| 卡片只有几行、下半屏空 | 否（数据量/行数问题） | 视觉上能变小，但内容不变 |
| 1440 列表/编辑页少量空 | 是（228px） | 否 |

## 3. 操作链影响

| 操作 | 480–560 抽屉里的结论 | 依据 |
|------|--------------------|------|
| 三级导航（列表→主体→状态） | **放得下，但退化为三步**：抽屉内无法同时放左栏与网格（rail 180 + 状态区 348 仍只能 1 列），只能用 面包屑/返回 逐级替换 | 2.3 的列数 |
| 状态编辑（改名/提示词/集数/接收位） | **放得下**：内容宽 448–528，小于编辑页 640 的字段上限；但集数 chip 会换行 2–3 行，面板更矮 | L1259 起字段 maxWidth 640 |
| 从资产库/画布「发送到主体」 | **需额外入口**：抽屉关闭时 `setCurrentSubjectStateContext` 已清空，`sendAssetToSubject` 必然走 460px 选择弹层；若自动开抽屉并定位，会打断画布右键操作 | `subject-send.ts` L30-73；当前唯一入口是画布右键 `use-node-actions.ts` L200-213 |
| @ 素材面板 vs 抽屉 | **会互相遮挡，且定位有风险**：300px 面板覆盖 480 抽屉的 62%；面板是 `position: fixed`，若抽屉用带 transform 的动画容器，fixed 子元素会改为相对抽屉定位并可能被裁剪 | L275-279 |
| 拖拽上传落区 | **不存在现状**：subject 目录无 `onDrop/dragover`；上传是面板内文件选择。若未来加，96px 槽位在 480 宽内放得下，垂直余量充足 | 全目录检索无拖拽处理 |
| 边看主体边看分镜 | **抽屉化后才能做到**：分镜全屏编辑器 `createPortal` 到同一个页签内容层，主体库是同一层的固定页签，现状互斥；并排还需分镜让出宽度 | `storyboard-sheet.tsx` L296-320；`editor-page.tsx` L1091-1113 |

## 4. 成本与风险

### 4.1 改动面

| 方案 | 必改文件 | 量级 |
|------|---------|------|
| A 全抽屉 | `subject-library-pages.tsx`（需宽度自适应/三步布局）、新抽屉壳、`canvas-tab-bar.tsx`、`canvas-tab-store.ts`、`editor-page.tsx`、`storyboard-tab-content.tsx`、`subject-page-nav.ts`、`navigate-to-view.ts`、`subject-send.ts`、`view-prefs.ts`、i18n ×3、4 个测试文件 | 12–14 个 |
| B 抽屉 + 保留整页 | A 的文件 + 双实例门控 + 入口按钮 + 记忆冲突处理 | 14–16 个，且双实例风险 |
| C 整页三栏（上次规格） | `subject-library-pages.tsx` + 3 个新子组件 + token 文件 + `subject-media-preview.tsx`（9:16 缩略）+ 顶栏一行 + i18n + 1 个测试文件 | 8–9 个，不碰页签/上下文/历史 |
| D 可调宽停靠 | A 的文件 + 宽度持久化 + 停靠/让位逻辑 | 14–16 个 |

### 4.2 关键风险

| 风险 | 说明 |
|------|------|
| 页签槽位模型 | 主体库是 4 个固定槽位之一；移除它要同步改默认顺序 localStorage、`lastSlotByProject` 可能残留 `'storyboard'`、`activateProjectEntry` 回落、`canvas-tab-slots.test.tsx` 与 `canvas-tab-restore.test.ts` |
| 双实例串台（B） | `editor-page.tsx` L1106-1111 同时挂载三个页级内容；再挂一个抽屉实例会出现两份 `container` 状态，各自整包写回，互相覆盖；`setCurrentSubjectStateContext` 是模块单例，两份都会登记，后写覆盖前者 |
| 历史/记忆 | `subject-page-nav.ts` 每级 `pushState`；抽屉"打开/关闭"若也入栈，浏览器后退会先关抽屉而不是回上一级，需要给 marker 增加 open 字段 |
| 发送直达 | 抽屉关闭 → 上下文为空 → 所有"发送到主体"都走弹层；抽屉打开 → 又要求"打开即定位 + 不打断当前操作"，需要新增 open + pending focus 协议 |
| @ 面板 | fixed + 300px；抽屉若使用 transform 动画会错位/裁剪，必须 portal 到 body 或改用非 transform 宽度动画 |
| 测试 | `subject-library-pages.test.tsx` 直接渲染 pages；抽屉化要保留 `data-subject-page` 钩子并新增 open/close 断言；`canvas-tab-slots.test.tsx` 渲染 `StoryboardTabContent` |

**保留整页作为「全屏管理」入口的可行性**：技术上可行（A + 一个入口），但 B 的双实例问题必须先解决——要么"同一实例搬家"（抽屉打开时卸载页签内容、关闭时恢复），要么把 pages 改成无状态受控组件。前者会带来层级闪烁与记忆同步，后者等于重写数据层，成本都不低。

## 6. 结论与各方案代价

### C（推荐）：维持整页，改成"用满屏幕"的工作台

- **做什么**：落地上次的单页三栏（左主体列表 / 中状态卡网格 / 右状态检查器）；列表页与编辑页的 `maxWidth: 1200` 取消或提到 1920，与状态页口径统一。
- **为什么**：留白的真实根因是三页各用一部分 + 列表/编辑页 1200 封顶（1920 空 708px）。三栏工作台把左栏与右栏常驻，屏幕被结构填满；宽度放开后 1920 列表 7 列、状态 6 列。
- **代价**：整页仍独占屏幕，无法边看画布/分镜；若这是硬需求，C 不满足。

### A（全抽屉）：不成立

- 480–560 → 状态卡 1 列、每屏 2 张，无法横向比对状态；三级导航变三步。
- 还要付页签槽位、历史、发送、@ 面板四项改造（12–14 文件）。
- 唯一收益是"不占整屏"。

### B（抽屉为主 + 整页入口）：不建议

- 抽屉同样受 1 列限制；整页入口意味着维护两套布局。
- 关键阻塞：页级内容三件套常驻挂载，双实例会各自维护 `container` 并整包回写，产生覆盖；发送上下文是模块单例，双实例会互相抢占。
- 若一定要 B，分工只能是：抽屉=快速定位+接收位（1 列、3 步），整页=批量管理（三栏）；并且必须保证同一时刻只有一个实例登记上下文、写容器。

### D（其它）：可调宽停靠面板（≥640，默认 720）

- 640 → 2 列（296px 卡），720 → 2 列（336px 卡）；2–3 行可见 4–6 张状态，够单主体 ≤6 状态使用。
- 画布/分镜可见，满足"边看边管"；但 3 步导航、页签槽位与历史改造仍要付，且无法容纳三栏工作台的右栏（≥1044 才够）。
- 适用条件：确认"主体库不占整屏"比"一屏看全状态"更重要。

## 7. 如果仍要抽屉：最小可行边界（供决策参考）

1. 宽度下限 640，推荐 720；**480–560 直接排除**（状态卡 1 列）。
2. 抽屉内必须是"三步 + 面包屑"，不能承诺三栏同屏；编辑器占满抽屉，@ 面板改为 portal 到 body 或内联底部 sheet（300px 面板不能压在 480 宽内容上）。
3. 单一实例：抽屉打开时卸载页签内容（或反之），禁止两份同时挂载。
4. 发送链路：`navigateToView('subject')` 改为"打开抽屉 + pending focus"，抽屉关闭时不登记上下文，发送仍走 `openSubjectLinkDialog`。
5. 历史：marker 增加 `open` 字段，避免"后退=关抽屉"；`view-prefs` 复用 `subjectPages.lastByProject`，再加 `drawerWidth`（仅 D）。

## 8. 需要拍板的点

1. **真实诉求是哪一个**：A）页面太空、希望密度更高 → 选 C；B）不想让主体库独占屏幕、要边看画布/分镜 → 选 D（≥640）。两者不能兼得。
2. **是否接受移除主体库的固定页签**（四槽位变三槽 + 抽屉/停靠）：这会改动页签顺序持久化、默认落地页和 3 个测试文件；若不接受，则只能选 C。
